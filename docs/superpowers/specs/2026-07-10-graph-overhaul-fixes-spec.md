## 0. Product decisions (override/extend the 2026-07-09 spec)

### 0.1 Retrieval posture split — live strict, chat liberal

- **Live/transcription path stays strict.** Nothing unsure is ever shown or summarized. Abstention remains empty-pack. C3 must be fixed *without* weakening validation: previously-*accepted* summary citations become re-citable (they were validated when accepted), and transcript-only summaries must be possible — but no unvalidated evidence ever enters a summary.
- **Chat gets a liberal fallback profile.** This is the "forked retrieval tool": not a second engine implementation (§11's shared-engine principle stands), but a chat/tool-mode fallback lane in the shared engine plus chat-side rendering:
  - New frozen field `RetrievalDecision.fallback: bool = False` (`retrieval/types.py`).
  - New engine option `fallback_on_abstain: bool` (constructor arg, set `True` by `RetrievalRuntime.make_engine` for modes `chat` and `tool`, `False` for `live`).
  - When the pre-PPR or post-rerank decision abstains AND `fallback_on_abstain` is set: assemble a bounded best-effort pack from the top calibrated dense/BM25 candidates that clear a **fallback floor** = `0.75 × acceptance_floor` of the respective head (computed from the artifact; no new artifact fields required, but read floors through one helper so it's swappable later). Cap: 4 passages, 0 facts, 0 paths, ≤1 passage per note. The pack's decision is `accepted=False, fallback=True, confidence=<top calibrated score>, reason="fallback_low_confidence"`. Passages are registered and marked read like normal evidence (they are shown to the model). If nothing clears the fallback floor, return the normal abstained empty pack (`fallback=False`).
  - Chat rendering (`chat/engine.py`): a fallback pack renders under an explicit header, e.g. `LOW-CONFIDENCE CONTEXT — retrieval did not clear its confidence floor; treat as hints, verify before asserting, and say so if you rely on it.` Facts/paths sections omitted. The abstention message (§14.2) is used only when the pack is truly empty.
  - `search_evidence` tool results from a fallback pack include `"low_confidence": true` per row.
  - Validation is unchanged — fallback passages are read evidence, so citing them is legal; NLI still gates claims. This keeps liberal retrieval from becoming liberal *assertion*.

### 0.2 Salience and extraction gating (M4 + Part 4)

Notes must carry salience, and extraction must be gated by salience — **more stringent than raw note length** (a short-but-salient note extracts; a long-but-junk note doesn't):

- **Plumbing:** connector records already carry `ingest_salience` through `registry.sync_connector` into the legacy store. The knowledge build must receive it: extend the record tuples passed from `extract_all_enabled`/`regenerate_knowledge` into `BuildCoordinator.build` so `write_note(..., ingest_salience=...)` persists the real value (default 1.0 when a connector doesn't set one).
- **Content-quality score** computed at build time per note, deterministic, cheap, in a new helper (suggested: `indexer/salience.py`): `content_quality ∈ [0,1]` from token count (saturating ramp, e.g. 0 tokens→0, ≥40 tokens→1 component), alpha-character ratio, unique-token ratio, and a repeated-line/boilerplate penalty. No LLM, no embeddings.
- **`note_salience = ingest_salience × content_quality`**, stored on the note row (reuse `ingest_salience` column for the connector part and add `salience` — or store the combined value in a new column; keep both inspectable in the build report).
- **Gating:**
  - Passages, FTS, and dense embeddings are ALWAYS built (searchability is never gated).
  - GLiNER extraction, entity mentions, facts, and base-graph entity participation run only for notes with `note_salience ≥ config.EXTRACTION_SALIENCE_FLOOR` (new knob, default 0.35). Gated notes get `extraction_status='skipped_low_salience'` (add to the CHECK constraint) — distinct from `failed`, never retried as an error, re-evaluated each build.
  - Value score (`_compute_note_ranks`) multiplies in salience (restores the legacy `ingest_salience` behavior) so the §6.6 completion gate becomes meaningful.
  - Build report: counts of gated notes per source + salience distribution summary.
- **Do not** gate on `len(text)` alone anywhere; length is only one input to `content_quality`.
